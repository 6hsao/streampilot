# 0001. 生产主链路采用阿里云 + 百炼托管模型

- 状态：Accepted
- 日期：2026-11-15
- 决策人：项目负责人（技术方向已定）

## 背景

系统需要在直播时段内稳定完成「评论接入 → 安全审核 → 生成 → 合成 → 渲染 → 推流」，对延迟、可用性和合规举证都有要求。团队规模有限，不宜自建模型推理与大规模媒体基础设施。

## 决策

生产主链路统一部署在**阿里云**：

- 生成：百炼 Qwen（qwen-plus 主力，qwen-turbo 快路径，qwen-max 兜底难题）
- 语音合成：CosyVoice（流式）
- 语音识别：Fun-ASR（仅非实时场景，不进主链路）
- 编排与业务：ECS（Docker Compose 起步）
- 队列与状态：Redis；业务数据：RDS MySQL；素材与媒体：OSS
- 内容安全：阿里云内容安全 + 本地词库 + 模型兜底
- 观测：OpenTelemetry + Prometheus/Grafana + SLS

**Azure 仅用于**：非实时实验、离线评测、后台任务与内容安全对照测试；不承载生产直播链路，不处理真实观众数据。

本地 Windows 只承担无法上云的职责：直播伴侣人工登录、推流凭据桥接、心跳与一键停播。

## 备选方案

| 方案 | 优点 | 不采用原因 |
| --- | --- | --- |
| 全 Azure | 与既有实验环境一致 | 与国内平台网络链路、备案、合规沟通成本更高；TTS/审核生态不在同一云 |
| 多云混合（生成一家、TTS 一家） | 规避单供应商风险 | 跨云延迟与计费复杂度上升，早期收益不抵成本 |
| 开源自建模型与 TTS | 单位成本可能更低 | 需要 GPU 运维与模型调优能力，稳定性风险高，偏离当前工程重点 |

## 影响

- 正面：同云内网调用、统一计费与配额、合规材料集中；延迟可控。
- 负面：存在供应商锁定；需通过 Gateway 层保留切换能力。
- 跟随改动：`llm-gateway`、`tts-gateway`、`safety` 均以适配器方式封装供应商调用；密钥统一走 KMS。

## 依据

- 前序调研结论（生产主链路走阿里云，Azure 仅实验用途）。
- 延迟预算要求（见 [ARCHITECTURE.md](../ARCHITECTURE.md#4-延迟预算)）需要同云低延迟调用。
- 合规要求需要审核、生成、存储证据链集中可查。
