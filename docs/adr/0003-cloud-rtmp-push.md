# 0003. 云端直接推 RTMP（架构 A）

- 状态：Accepted
- 日期：2026-11-15
- 决策人：项目负责人

## 背景

本地 Windows 只能完成直播伴侣登录与凭据获取，不适合作为长期推流节点（网络、稳定性、运维与安全都不可控）。需要确定画面合成后的推流位置。

## 决策

- 采用**架构 A**：云端渲染 + 云端 Streamer 使用固定出口 IP 直接推 RTMP。
- 本地职责收敛为：人工登录直播伴侣、读取/确认推流地址、通过 mTLS 上报、心跳、一键停播；**不推流**。
- 推流地址与 key 只允许内存与 KMS 密文引用；Streamer 单写者独占；收播即吊销。
- 开播前强校验平台书面许可/报备记录（`LIV-07`）。

## 备选方案

| 方案 | 优点 | 不采用原因 |
| --- | --- | --- |
| 架构 B：本地伴侣推流 + 画面回传 | 更贴近平台默认使用方式 | 本地成为单点；画面回传增加延迟与带宽；多云边协同复杂 |
| 混合：云端渲染、本地推流 | 兼顾画质与平台兼容 | 仍需本地稳定运行推流器，运维成本未降低 |

## 影响

- 正面：推流可集中监控、重连与灰度；渲染与推流同机减少一跳；便于多机位扩展。
- 负面：**依赖平台对第三方/云端推流的许可**；推流地址泄露会带来盗播与封号风险；云端网络抖动直接影响直播。
- 缓解：M0 取得书面许可并登记 IP；`LIV-08` 防泄露与串流监测；备用节点 + 断流重连；保留架构 B 回退预案。
- 跟随改动：`GOV-05`、`LIV-01/02/03/07/08`、`DEPLOYMENT` 拓扑与 Runbook、`PLAN` 风险 R-01/R-06/R-13。
