# 0004. 首发只做抖音单平台、单直播间

- 状态：Accepted
- 日期：2026-11-15
- 决策人：项目负责人

## 背景

产品链路涉及平台接入、审核、生成、合成、渲染、推流与人工接管。若同时做多平台与多直播间，会显著放大资质、适配、隔离与运维复杂度，稀释对单链路质量的投入。

## 决策

- 首发范围：**抖音单平台 + 单直播间 + 单租户**。
- 代码保留扩展点：`ingest-<platform>` 适配器边界、按 `session_id` 分区、租户字段。
- 多直播间、多租户、第二平台、语音互动、3D 列入 **Post-1.0**，不在本期验收。

## 备选方案

| 方案 | 优点 | 不采用原因 |
| --- | --- | --- |
| 首发即多平台 | 覆盖面广 | 资质与适配成本高，单链路质量难保证 |
| 首发即多间 | 摊薄成本 | 隔离、调度、配额未验证，故障面扩大 |
| 只做单平台单间 | 聚焦、可验证 | 短期规模受限（已接受） |

## 影响

- 正面：验收标准清晰，资源与预算可精确核算，合规举证简单。
- 负面：商业化规模后置；需要克制“顺手抽象”。
- 跟随改动：`PLAN` 范围与 M7、`README` 路线图、`OPS-03` 降为 Post-1.0、`ARCHITECTURE` 扩展路径。
